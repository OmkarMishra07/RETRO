3. The InnerTube Client — the real engine
The app communicates with YouTube Music's backend through a custom implementation of the InnerTube API, the protobuf-based internal interface used by official YouTube clients. Grokipedia
You already have ytmusicapi — that's exactly this. For the stream URL specifically, instead of yt_dlp (which is slow and heavy), you call InnerTube's /youtubei/v1/player endpoint directly:
python# What Metrolist does — directly hitting InnerTube player endpoint

This is fast (no spawning yt_dlp processes), returns audio URLs directly, and is exactly what Metrolist does.

4. The Critical Architecture Decision
Return the CDN URL to the browser — don't proxy audio through your server.
❌ Wrong: Browser → Your server → YouTube CDN → Your server → Browser
✅ Right:  Browser → Your server (gets URL) → Browser → YouTube CDN directly
Your /stream/:videoId endpoint just returns the URL string. The browser's <audio src="..."> then fetches from YouTube's CDN directly — your server never touches the audio bytes. This is how Metrolist works on a device and what makes it scalable.

5. Redis Cache — absolutely essential
Stream URLs are valid for ~6 hours. Cache them:
python# Pseudocode
def get_stream(video_id):
    cached = redis.get(f"stream:{video_id}")
    if cached:
        return cached
    
    url = innertube_get_stream_url(video_id)
    redis.setex(f"stream:{video_id}", 21600, url)  # 6hr TTL
    return url
Also cache search results (5 min TTL) and lyrics (permanent).
